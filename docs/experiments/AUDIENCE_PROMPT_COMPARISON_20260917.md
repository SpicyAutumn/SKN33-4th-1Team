# 수준별 답변 프롬프트 비교 결과

2026-09-17 · 실험 결과 요약 · 후보 서비스 미적용

## 목적과 결론

기존 생성 답변의 문제를 보완하여, 품질 개선이 확인된 프롬프트를 실제 서비스에 반영하는 것이 목적이었다. 같은 질문과 근거로 기존 방식·첫 수정안(v1)·두 번째 수정안(v2)을 순차 비교했다.

**일부 설명은 개선됐지만 주요 오류가 남거나 재발했다. 수정안을 기존 방식 대신 적용할 만큼 일관된 개선 근거를 확보하지 못해 v1/v2 전체 적용은 진행하지 않았다.** 기존 방식이 충분히 정확하다는 뜻은 아니며, 기존과 후보 모두 미해결 문제가 있다.

## 현재 서비스와 이 보고서의 구분

2026-09-17 확인 기준은 PR #12·#13이 병합된 main `468cb7f`다. **아래 72개 답변은 당시 고정한 요청으로 수집한 과거 실험 결과이며, 현재 서비스의 답변 품질을 다시 측정한 결과가 아니다.**

| 구분 | 이번 비교 실험 | 현재 main에서 확인한 변경 |
|---|---|---|
| 생성 지시와 출력 | 당시 6개 출력 필드, 기존·v1·v2 지시 비교 | `response-type-v2-summary-ollama`: `summary`와 한국어 1~2문장 요약 지시 추가 |
| 요약 누락 | 새 `summary`의 품질을 평가하지 않음 | 구형 응답에서 요약만 빠지면 본문으로 보완하는 호환 처리 |
| 후처리 | 아래에 명시한 두 고정 커밋으로 대조 | PR #5는 이후 보완 중이며, 최신 변경을 72개에 재적용하지 않음 |
| 화면·연결 | 고정 문맥을 사용한 독립 생성 평가 | React → `/api/v1/searches` → Django → 기존 RAG 연결 구현 |

새 요약 지시가 전체 답변에 미치는 영향은 이번 실험으로 확인하지 않았다. 과거 결과만으로 현재 요약 품질을 평가하거나, 반대로 서비스 변경만으로 기존 사실 오류가 해결됐다고 판단하지 않는다. 본 보고서의 **후보 미채택 결론과 문항별 판정은 그대로 유지**한다.

## 비교를 진행한 순서

‘실험 단계’는 프롬프트 버전을 바꾼 순서이고, ‘반복 회차’는 같은 버전으로 같은 입력을 다시 생성한 횟수다.

| 단계 | 수집 구성 | 새 답변 수 | 무엇과 비교했는가 |
|---|---|---:|---|
| 1. 기존 방식 | 4문항 × 3수준을 1회차와 2회차에 각각 실행 | 12 + 12 = 24 | 두 회차에서 드러나는 오류와 수준별 설명을 검토 |
| 2. v1 | 동일한 12개 조합을 두 번 실행 | 12 + 12 = 24 | 저장된 기존 24개와 비교. 기존 답변은 다시 생성하지 않음 |
| 3. v2 | 동일한 12개 조합을 두 번 실행 | 12 + 12 = 24 | 저장된 기존·v1 각 24개와 비교. 이전 답변은 다시 생성하지 않음 |

총 72개는 **서로 다른 질문 72개가 아니라, 4문항의 수준·반복·프롬프트 버전별 답변**이다. 각 회차는 L01 쉬움→일반→깊이 있게부터 L04까지 같은 순서로 진행했다. 같은 입력에서도 오류가 달라질 수 있어 두 번 실행했으나, 두 번으로 오류 발생률을 추정하거나 통계적 우위를 입증하려는 실험은 아니다.

## 비교 조건과 검토 방법

- 모델: `exaone3.5:7.8b-instruct-q8_0`, 동일 모델 식별값(해시), Ollama 0.34.0, A40.
- 동일 질문·출처·출력 JSON 형식·생성 무작위성 설정(temperature) 0·수준별 생성 상한(384/640/1024 토큰)을 유지했다.
- 검색·임베딩·준비 생성·자동 재시도 없이 저장 문맥으로 생성했다. 최초 실제 요청 300초, 이후 120초 제한을 적용했다.
- 문항·수준별 기존 2개 + v1 2개 + v2 2개를 모두 검토했다. 좋은 회차만 선택하지 않았다.
- 원문 기준 사실 관계·질문 충족·수준별 설명·명확성을 먼저 검토했다. 후처리는 원문 복사본에 따로 적용했다.
- 사용자 검토를 거쳐 기존, v1, v2의 문항별 판정을 확정했다. 새 기준을 만들어 과거 실패를 통과로 바꾸지 않았다.

기존 생성 평가 기준의 고정 문맥 및 원문/후처리 분리 원칙을 따르되, 이번은 **오류 사례 중심의 제한 평가**다. 정식 100점 채점 전체, 최종 서비스 응답 계약, 실제 UI 통합 시험까지 마친 결과가 아니다.

두 회차 본문이 완전히 같은 조합은 기존 7/12, v1 5/12, v2 11/12였다. 이 수치에는 같은 오류의 반복도 포함되므로 품질·안정성 점수로 사용하지 않는다.

### 고정 후처리 대조

기준 코드 `1d48186168c024c547f17f619c1530ff3bd6ca8a`와 PR #5의 `61009ee0d4f2d6c25c1ac2518a9e3bcf5e48e58e`를 사용해 문맥 ID 복원·정정 정규화·ID 보정을 오프라인 적용했다. 각 버전의 24개 모두 두 코드 사이에 결과 차이가 없었고, 본문·응답 유형도 원문 대비 바뀌지 않았다. 문맥 ID 복원은 별도다.

이는 이번 입력과 고정 코드에 대한 결과이지 PR #5 전체 효과를 부정하거나 최신 서비스 전체를 검증한 결과가 아니다. 화면 표시 개선도 생성 내용의 사실 오류를 직접 해결하는 기능과 구분한다.

## 왜 반영하지 않았는가

1. 일부 문항 개선과 함께 중요한 오류가 남거나 새로 나타나 일관된 개선이라고 보기 어려웠다.
2. v1에서 줄었던 오류가 v2에서 재발했다. 지시를 더 구체화하는 것만으로 정확성이 보장되지 않았다.
3. 기존 답변에도 문제가 있으나 검증되지 않은 대체안 적용이 그 문제를 해결한다고 볼 근거가 부족했다.
4. 추가 답변 수집으로 원인을 좁힐 수 있지만, 호출 수 증가 자체가 개선을 보장하지는 않는다. 남은 일정과 새로운 접근을 검토할 필요를 함께 고려했다.

따라서 이번에는 유료 반복을 멈추고 결과와 미해결 사항을 정리한다. ‘개선 근거 부족’은 통계 검정 결과가 아니라 **서비스 반영을 뒷받침할 일관된 개선을 확인하지 못했다는 의미**다. 부분적으로 좋았던 문구를 임의로 조합한 새 프롬프트도 검증된 후보로 취급하지 않는다.

## 원인 점검과 남은 업무

실제 요청에는 정정 지시와 필요한 사실 근거가 있었다. 출력 형식도 정정 응답을 허용했다. 특정 버전의 잘못된 전송이나 정정 출력 금지는 확인되지 않았다.

다만 근거가 충분하다는 상태와 질문 전제의 정확성 구분, 응답 유형과 정정 상세의 연결, 설명 확장 요구는 후속 점검 대상이다. 이 요소가 단일 원인이라는 증거는 없으며 출력 스키마 변경만으로 해결된다고 주장하지 않는다.

| 완료 | 미완료·미실행 |
|---|---|
| 3단계 수집·원문 비교·사용자 판정 검토 | 전반적인 수준별 품질 개선 입증 |
| 고정 후처리 비교·실제 요청 점검 | 단일 원인 확정·해결 효과 검증 |
| 입력·원문·로그 로컬 보존 | 후보 운영 적용·H 확인·최신 서비스 연결 시험 |

후속 작업은 지시문 구성과 응답 유형 선택·검사 방식의 개선 방향을 재검토하되, 실제 프롬프트·모델 설정·검증 단계·응답 형식을 변경하기 전에는 관련 업무 담당자에게 영향과 범위를 안내한다. 이번 문서는 해당 변경이나 추가 호출의 승인이 아니다.

## 자료의 한계와 공개 범위

새 Pod의 물리 호스트·드라이버·캐시 차이가 있어 속도 우위를 결론 내리지 않는다. 소수 개발 사례의 결과를 전체 문화유산 질의나 다른 모델로 일반화하지 않는다.

공개 자료에는 결과 요약만 담는다. 실제 원문·출처 전문·서버 로그·개인 환경 정보는 로컬에 보존한다. **이 요약만으로 실측 결과를 재계산할 수는 없다.** 본문은 서비스 코드나 현재 모델 설정을 변경하지 않는다.
