# 질문의 잘못된 전제 교정 — 기존 구현·테스트 대응표

## 목적과 기준

‘대상 문장이 출처와 맞는지 검사’하는 기능과 ‘사용자의 잘못된 질문을 바로잡아 답변’하는 기능을 구분한다. 역할 구분·보조 평가 기준·설명용 예시·실제 변경 전 담당자 확인에 대한 사용자 검토를 완료했다. 팀의 구현 변경 승인은 아니며 기존 가중치·점수·응답 구조·검증 규칙은 바꾸지 않는다.

## 팀원 검토 후 진행 방향

[팀원 검토 댓글](https://github.com/SpicyAutumn/SKN33-4th-1Team/pull/4#issuecomment-5673991762)을 반영했다. 다음은 현재 작업 방향이며 팀 전체의 구현 승인이나 표시 방식 확정을 의미하지 않는다.

| 항목 | 반영한 방향 | 남은 결정 |
|---|---|---|
| 문서 | 내부 검토 식별값을 검토 내용으로 풀어 씀 | 문서 PR 검토·병합 |
| D01 | 표시 예시를 기준으로 UI·서비스 담당자가 결정 | 정정 요약만 표시 / 전체 설명 함께 표시 |
| D02 | 확인된 문구 정리 우회 경로를 회귀 테스트와 최소 수정의 우선 대상으로 준비 | 적용 조건·정상 응답 보호 범위 사전 확인 후 별도 구현 PR |
| D03 | 운영 환경의 전체 단계 저장 확대는 당장 추진하지 않을 예정 | 구체적인 장애 분석 요구가 생기면 개인정보·보관 기간·비용을 포함해 별도 설계 |
| 추가 모델 실험 | 현재 계획하지 않음 | 필요 시 문항 선정·목표 수·반복 횟수·채택/제외 및 종료 기준부터 정함 |

D03의 운영 기능 확대를 미루더라도 기존 오프라인 평가의 원문 보존과 단계별 구분 원칙은 유지한다.

2026-09-15에 확인한 main `f2373d896dfac9c16fae98958ae4d6172cb49027`의 코드와 테스트를 정적으로 읽었다. 테스트 실행·실제 화면 재현·모델 호출은 하지 않았다. 아래 ‘존재’는 구현/테스트가 있다는 뜻이지 모든 실제 응답이 기준을 통과한다는 뜻은 아니다.

기존 [생성 평가 기준](track_b/04_generation_evaluation_criteria.md)은 이미 원본과 서비스 결과 분리, 근거 일치·질문 충족·명확성 평가를 정의한다. 새 기능이 전혀 없다는 전제에서 출발하지 않는다.

|---|---|---|---|
| D01 | UI·배포, RAG Chain·서비스 | 교정 카드는 전체 답변보다 `corrected_premise`(정정 내용) 필드를 우선 표시·낭독 | 정정 내용만 보여줄지, 전체 답변도 함께 보여줄지. 잘못된 부분과 올바른 사실을 모두 전달하는 표시 예시 제시 |

### D01 — 화면에서 정정 내용을 충분히 전달하는가?

확인한 코드는 `corrected_premise`가 있으면 전체 `message` 대신 그 값을 표시하고 음성으로 읽는다. 생성 코드가 이 필드를 답변의 첫 문장으로 만들 수 있으므로, 질문 오류를 설명한 뒤 문장이 카드에서 빠질 수 있다.

| 설명용 예시 | 내용 |
|---|---|
| 전체 답변 | ‘1442년입니다. 질문의 1441년은 올바른 연도가 아닙니다.’ |
| 첫 문장만 담긴 정정 필드 | ‘1442년입니다.’ |
| 검토할 차이 | 사실은 전달하지만 질문의 어떤 부분이 잘못됐는지는 직접 표시하지 않음 |

이는 코드 경로를 설명하기 위한 작성 예시이며 실제 화면 장애를 재현한 결과가 아니다. **UI·서비스 담당자는 현재 표시 유지 또는 변경 제안과 함께, 사용자에게 보여줄 문구 예시를 알려주면 된다.**

### D02 — 모든 교정 경로에서 자기모순을 확인하는가?

생성 코드에는 ‘네, 맞습니다’ 같은 시작 표현을 제거하는 함수가 있지만, 교정 상세 필드와 출처 ID가 이미 있는 분기는 이 함수 호출 전에 반환한다. 관련 연도 테스트의 입력에는 해당 긍정 시작이 없으므로 그 테스트만으로 제거 동작을 확인했다고 볼 수 없다.

팀원은 이 경로를 회귀 위험으로 지적했다. 코드를 읽으면 문구 정리를 우회하는 경로가 확인되므로, 단순한 가능성 문의에서 **회귀 테스트와 최소 수정 범위의 사전 확인**으로 다음 작업을 좁힌다. 잘못된 긍정 시작과 교정 상세가 함께 있는 응답, 올바른 질문에 정상적으로 동의하는 응답을 함께 확인할 예정이다. 실제 테스트 실행과 수정은 별도 구현 범위이며 실제 서비스 발생 빈도는 아직 확인하지 않았다.

### D03 — 어느 단계에서 달라졌는지 기록할 수 있는가?

확인할 기록은 **모델 원본 → 서비스 보완 결과 → 실제 표시 문구**다. 검색 문맥을 저장한 기록은 모델 원본을 저장한 기록과 다르다. 확인한 생성 함수의 반환값만으로는 세 단계가 모두 보존된다고 판단할 수 없다.

위 내용은 기록상의 한계로 남기되 운영 저장 기능을 당장 추가하지 않을 예정이다. 기존 오프라인 평가 자료를 보존하며, PC 기준은 보조 검토 항목으로 유지하고 새 총점에 합산하지 않는다. 운영 기록 확대는 구체적 필요가 생긴 뒤 별도 설계한다.

## 보조 평가 방법

질문 속 검사 대상, 출처의 지지/반박/부족/충돌/모호 상태, 올바른 사실, 근거 위치와 허용 해석을 먼저 기록한다. 같은 대상·사건·시점인지 확인한 뒤 확보된 출력 단계만 평가한다.

평가 축은 사실 정확성·교정 명확성·근거 적합성·답변 내 일관성·응답 형식이다. 각 축을 다음처럼 구분하며 새 총점을 만들지 않는다.

- 적합: 해당 기준 충족.
- 부분 충족: 사실은 맞지만 구분·설명 일부 부족.
- 문제: 잘못된 교정·근거 없는 단정·자기모순 등 확인.
- 해당없음: 올바른 질문처럼 교정 자체가 필요하지 않은 경우.
- 미검토: 출력이나 근거가 없거나 아직 확인하지 않은 경우. 통과로 처리하지 않음.

### PT01~PT08 — 수동 작성 예시, 실행된 테스트 아님

| 예시 | 상황 | 제안 판정 |
|---|---|---|
| PT01 | 출처는 1442년, 질문은 1441년. ‘1441년이 아니라 1442년입니다’ | 사실·명확성 적합. ‘아니요’라는 단어는 필수 아님 |
| PT02 | 같은 조건에서 ‘1442년입니다’만 말함 | 사실 적합, 교정 명확성 부분 충족 |
| PT03 | ‘네, 맞습니다’ 뒤에 질문과 다른 연도 제시 | 답변 내 일관성 문제 |
| PT04 | 연도 근거 없이 ‘아니요, 1442년입니다’ | 근거 없는 정정 |
| PT05 | 맞는 질문을 ‘아니요’로 부정 | 잘못된 부정 |
| PT06 | 발명 연도를 제도 확정 연도로 대체 | 대상 관계·시점 혼동 |
| PT07 | 서로 충돌하는 출처의 차이를 해소하지 못함 | 단정 교정 보류, 출처 범위·사건 차이 확인 |
| PT08 | 교정 필드는 맞지만 화면은 틀린 전제에 동의 | 구조와 표시 일관성을 분리해 문제 기록 |

이 예시는 역사 사실에 대한 새로운 조사 결과나 실제 모델 발췌가 아니다. 기존 IC01 적합 판정 등 과거 결과를 소급 변경하지 않는다.

## 역할과 PR 범위

[기존 역할 문서](track_b/01_role_and_scope.md)에 따라 생성은 지시문·생성 구간, RAG 통합은 최종 유형·근거·출처, UI는 화면 표시를 맡는 구분을 유지한다. 문서 일부에는 검토 예정 상태가 남아 있으므로 이를 새로운 인력 배정이나 최신 전체 합의로 단정하지 않는다.

이번 PR은 [후속 결과](CLAIM_COMPARISON_FOLLOWUP.md)와 이 대응표만 공유한다. 실제 코드·프롬프트·화면 변경은 관련 담당자 의견 후 별도 구현 범위로 정한다.

팀 전체에 역할을 다시 정해 달라고 묻기보다 D01~D03 중 실제 변경이 필요한지 좁혀 검토한다.

```text
검토 항목: D01 / D02 (D03은 운영 확대 필요가 생길 때)
관련 기능:
의견: 현행 유지 / 추가 확인 / 별도 변경 제안
D01: 표시 유지/변경 의견과 표시 문구 예시:
D02: 회귀 테스트·최소 수정 범위에 대한 의견:
D03: 구체적인 운영 기록 확대 필요가 있는 경우에만 기재:
검토하지 않은 항목은 비워 두어도 됩니다.
```
