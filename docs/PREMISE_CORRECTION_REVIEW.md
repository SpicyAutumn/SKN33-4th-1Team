# 질문의 잘못된 전제 교정 — 기존 구현·테스트 대응표

## 목적과 기준

‘대상 문장이 출처와 맞는지 검사’하는 기능과 ‘사용자의 잘못된 질문을 바로잡아 답변’하는 기능을 구분한다. PC-A~D 사용자 검토를 완료한 보조 기준이며 팀의 구현 변경 승인은 아니다. 기존 가중치·점수·응답 구조·검증 규칙은 바꾸지 않는다.

2026-09-15에 확인한 main `f2373d896dfac9c16fae98958ae4d6172cb49027`의 코드와 테스트를 정적으로 읽었다. 테스트 실행·실제 화면 재현·모델 호출은 하지 않았다. 아래 ‘존재’는 구현/테스트가 있다는 뜻이지 모든 실제 응답이 기준을 통과한다는 뜻은 아니다.

기존 [생성 평가 기준](track_b/04_generation_evaluation_criteria.md)은 이미 원본과 서비스 결과 분리, 근거 일치·질문 충족·명확성 평가를 정의한다. 새 기능이 전혀 없다는 전제에서 출발하지 않는다.

## 읽을 코드

- S: [서비스 코드](../src/rag_service/service.py)의 `_validate_premise_correction`, `_finalize` 및 생성 결과 검증.

- TG: [생성 테스트](../tests/test_ollama_generator.py), TS: [서비스 테스트](../tests/test_rag_service.py).

## PC01~PC07 대응표

| 기준 | 기존 구현·규칙 | 확인한 기존 테스트 | 남은 범위 |
|---|---|---|---|

| PC02. 틀린 부분과 올바른 사실을 분명히 전달 | G 지시문에 두 내용을 바로 설명하라는 규칙 존재. U는 교정 필드 우선 표시 | TG의 `test_answer_that_states_question_year_was_wrong_becomes_corrected_premise` | 이 테스트는 교정 필드가 첫 문장인 것을 확인함. 전체 답변의 명시적 교정이 최종 표시에서도 유지되는지는 별도 확인 |
| PC03. 대상·관계·시점을 유지 | G에 연도·인물·분류 교정 예시와 모호성/근거 부족 구분 지시 존재 | TG의 `test_answer_that_explicitly_corrects_assertion_becomes_corrected_premise`, `test_plain_answer_with_negative_sentence_is_not_reclassified` | 확인한 테스트는 유형 변경 중심. 발명/확정 시점 혼동, 맞는 질문 일부까지 부정하는 경우는 별도 대조 사례 필요 |
| PC04. 교정 내용과 근거 연결 | S가 허용 ID·교정 출처 존재를 검사하고 사용 출처와 교정 출처를 합쳐 중복 제거 | TS의 `test_corrected_premise_builds_citation_from_correction_evidence`, `test_corrected_premise_citation_union_preserves_first_occurrence_order` | 구조·ID 검사와 의미상 충분성은 별개. M의 문서 ID 지표를 정확한 구절 인용 또는 내용 지지 검사로 부르지 않음 |
| PC05. 틀린 전제 동의 등 자기모순 방지 | G 지시문에 ‘네, 맞습니다’로 시작하지 않기. `_clean_correction_message`는 특정 시작 표현 제거 | TG 연도 교정 테스트에 해당 시작이 아님을 확인하는 assertion 존재 | 그 입력 자체에는 잘못된 긍정 시작이 없음. 제거 동작의 직접 검증으로 간주하지 않음. 교정 상세 필드가 이미 있는 분기는 문구 정리 전 반환함 |

| PC07. 원본·자동 보완·표시 결과 구분 | 기존 평가 문서에 원본/최종 결과 분리 명시. G는 응답 파싱 후 보완하고 보완 결과를 반환 | TS의 `test_answer_with_trace_reuses_one_search_and_keeps_unselected_contexts`는 검색 문맥 보존 테스트 | 검색 trace가 생성 원문 보존을 증명하지 않음. 확인한 G 반환값에는 보완 전 원문과 표시 문구를 별도 묶어 반환하는 항목이 없음. 전체 기록 경로 완비 여부는 별도 확인 |

위 테스트는 관련된 좁은 행동을 확인하는 자료다. PC 기준 전체를 만족하는 테스트 세트라고 주장하지 않는다. [PR #2의 기록 도구](../experiments/semantic_verifier/offline_record.py)는 독립 평가용이며 서비스 원본·표시 기록 기능을 대신하지 않는다.

## 구체적으로 좁힌 확인 사항

### D01. 교정 카드가 보여 줄 내용 — UI·서비스 검토

현재 U는 `corrected_premise`가 있으면 전체 `message` 대신 그 값을 표시하고 음성으로 읽는다. G가 자동 조립할 때 이 필드를 첫 문장으로 만들 수 있다. TG 연도 예시도 첫 문장은 올바른 연도만 제시하고 질문의 틀린 연도 설명은 뒤 문장에 있다.

따라서 이 조합에서는 교정 카드에서 명시적 대비가 빠질 가능성이 있다. 실제 서비스 장애를 재현한 결론은 아니다. 기존 표시 방식을 유지할지, 전체 답변과 교정 내용을 함께 표시할지는 담당자 검토 사항이다. 원래 전제를 그대로 재노출할 경우 불필요한 민감 내용 표시도 검토해야 한다.

### D02. 자기모순 정리의 적용 경로 — 생성·서비스 검토

G는 교정 상세 필드와 출처 ID가 이미 있으면 유형을 맞추고 반환한다. 특정 잘못된 긍정 시작 제거는 별도 분기에서 실행된다. 모든 교정 응답에 문구 정리가 적용된다고 가정하지 않는다. 먼저 해당 분기와 정상 답변을 함께 확인할 오프라인 테스트 범위를 검토한다. 곧바로 정규식을 확대하거나 자동 수정하지 않는다.

### D03. 기록과 평가의 연결 — 생성·통합 평가 검토

M은 응답 유형·보류·문서 ID 출처 지표·지연을 계산하며 내용 충실성은 별도 평가 영역이라고 명시한다. PC 기준은 기존 생성 평가의 보조 체크리스트로 검토한다. 기존 점수에 자동 합산하지 않는다. 원본·보완 결과·표시 문구를 어디에 보관하고 어떻게 연결할지 확인하되, 서비스 응답에 원문을 무조건 추가하지 않는다.

## 보조 평가 방법

질문 속 검사 대상, 출처의 지지/반박/부족/충돌/모호 상태, 올바른 사실, 근거 위치와 허용 해석을 먼저 기록한다. 같은 대상·사건·시점인지 확인한 뒤 확보된 출력 단계만 평가한다.

평가 축은 사실 정확성·교정 명확성·근거 적합성·답변 내 일관성·응답 형식이다. 각 축을 다음처럼 구분하며 새 총점을 만들지 않는다.

- 적합: 해당 기준 충족.
- 부분 충족: 사실은 맞지만 구분·설명 일부 부족.
- 문제: 잘못된 교정·근거 없는 단정·자기모순 등 확인.
- 해당없음: 올바른 질문처럼 교정 자체가 필요하지 않은 경우.
- 미검토: 출력이나 근거가 없거나 아직 확인하지 않은 경우. 통과로 처리하지 않음.

### PT01~PT08 — 수동 작성 예시, 실행된 테스트 아님

| 예시 | 상황 | 제안 판정 |
|---|---|---|
| PT01 | 출처는 1442년, 질문은 1441년. ‘1441년이 아니라 1442년입니다’ | 사실·명확성 적합. ‘아니요’라는 단어는 필수 아님 |
| PT02 | 같은 조건에서 ‘1442년입니다’만 말함 | 사실 적합, 교정 명확성 부분 충족 |
| PT03 | ‘네, 맞습니다’ 뒤에 질문과 다른 연도 제시 | 답변 내 일관성 문제 |
| PT04 | 연도 근거 없이 ‘아니요, 1442년입니다’ | 근거 없는 정정 |
| PT05 | 맞는 질문을 ‘아니요’로 부정 | 잘못된 부정 |
| PT06 | 발명 연도를 제도 확정 연도로 대체 | 대상 관계·시점 혼동 |
| PT07 | 서로 충돌하는 출처의 차이를 해소하지 못함 | 단정 교정 보류, 출처 범위·사건 차이 확인 |
| PT08 | 교정 필드는 맞지만 화면은 틀린 전제에 동의 | 구조와 표시 일관성을 분리해 문제 기록 |

이 예시는 역사 사실에 대한 새로운 조사 결과나 실제 모델 발췌가 아니다. 기존 IC01 적합 판정 등 과거 결과를 소급 변경하지 않는다.

## 역할과 PR 범위

[기존 역할 문서](track_b/01_role_and_scope.md)에 따라 생성은 지시문·생성 구간, RAG 통합은 최종 유형·근거·출처, UI는 화면 표시를 맡는 구분을 유지한다. 문서 일부에는 검토 예정 상태가 남아 있으므로 이를 새로운 인력 배정이나 최신 전체 합의로 단정하지 않는다.

이번 PR은 [후속 결과](CLAIM_COMPARISON_FOLLOWUP.md)와 이 대응표만 공유한다. 실제 코드·프롬프트·화면 변경은 관련 담당자 의견 후 별도 구현 범위로 정한다. 확인 시 열린 4차 PR #3는 미디어 데이터 처리 작업이며 이 생성·교정 코드를 변경하지 않았다. 과거 3차 문서 안의 PR 번호와 현재 4차 PR 번호는 구분한다.

팀 전체에 역할을 다시 정해 달라고 묻기보다 D01~D03 중 실제 변경이 필요한지 좁혀 검토한다.

```text

관련 기능:
의견: 현행 유지 / 추가 확인 / 별도 변경 제안
근거 또는 이미 충족하는 경로:
변경이 필요하다면 제안 범위:
```
