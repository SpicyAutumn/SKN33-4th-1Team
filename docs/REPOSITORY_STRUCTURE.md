# 파일을 두는 기준

## 실행·개발·기록의 구분

| 위치 | 역할 | 새 파일을 추가할 때 |
|---|---|---|
| `frontend/src/components/` | 제품 화면 | 시안 코드를 import하지 않는다 |
| `frontend/src/review/` | 모의 데이터·수동 화면 검사 | 제품 컴포넌트를 재사용하고 진입 HTML과 사용법을 기록한다 |
| `backend/` | Django API·인증·DB·웹 설정 | 모델·API 변경에 필요한 migration과 검사를 함께 추가한다 |
| `app/` | Django와 RAG·연관 탐색 연결 | 실제 호출되는 연결 코드만 둔다 |
| `src/` | 재사용 가능한 데이터·검색·생성·평가 구현 | 운영 구현과 실험 대안을 구분한다 |
| `experiments/` | 실험 구현·입력·오프라인 검사 | 운영 코드가 실험 코드를 import하지 않게 한다 |
| `scripts/` | 데이터 준비·검증·배포 CLI | 실행 인자와 외부 API/DB 사용 여부를 명시한다 |
| `scripts/archive/` | 특정 과거 데이터에 종속된 도구 | 당시 조건과 현재 용도로 사용할 수 없는 이유를 기록한다 |
| `tests/` 및 각 앱의 검사 폴더 | 자동 회귀 검사 | 유지하는 기능의 검사를 코드와 함께 관리한다 |
| `data/` | manifest·평가 문항·데이터 준비 경로 | 원본·대형 인덱스·비공개 자료는 Git 제외 규칙을 따른다 |
| `outputs/` | Git에서 명시적으로 보존하는 검증 근거 | 검증에 쓰이는 결과만 선별하여 추적한다 |
| `output/`, `_local/` | 로컬 생성물·개인 초안 | Git과 Docker 빌드에 포함하지 않는다 |

## 문서의 기준

- `docs/deliverables/`: 4차 제출 요약. 상세 설명은 해당 문서에 연결한다.
- `docs/api/`와 운영·데이터 문서: 현재 구현·실행 방법. 특정 브랜치 작업 당시 안내를 현재 절차처럼 남기지 않는다.
- `docs/experiments/`: 비교 조건·결과·한계를 포함한 평가 근거.
- `docs/archive/`: 초기 역할·제안·시안·이전 차수 자료. 작성 시점과 현재 안내를 구분한다.
- 구성도 상세는 `docs/03_system_architecture.md`, 제출·배포 요약은 `docs/deliverables/03_architecture.md`를 사용한다.

## 이동·삭제 확인

파일 이동 시 코드 import, CLI의 프로젝트 루트 계산, CI 명령, 문서 상대 링크를 함께 수정한다. 이미지가 저장소 문서에 연결되지 않아도 GitHub PR의 증거일 수 있으므로 외부 참조를 확인한다. 빈 `__init__.py`와 과거 migration은 일반 임시 파일로 취급하지 않는다.

`.worktrees/`는 독립 작업 브랜치가 연결된 로컬 폴더다. 파일 정리 목적으로 통째로 삭제하지 않는다. 폴더 이름 변경만으로 파일 수나 저장소 용량이 줄지는 않는다.
